# Shared organization header

Core Platform includes a shared header with authorized app links, personal pins,
account tools, and Chat. Chat opens in a drawer: read conversations, send messages,
see unread/mention notifications, and change each conversation's notification mode
without navigating away from an application. The full Chat workspace remains
available for conversation creation, groups, search, sharing, and administration.

## Configure it as an administrator

1. Open your organization's **Central admin → Shared application header**.
2. Set the platform name, a public HTTPS logo URL, a color scheme (Navy, Slate,
   Forest, Light, or custom colors), comfortable/compact spacing, and whether to
   show the organization name. Custom header text/background colors must meet
   4.5:1 contrast. The editor previews unsaved changes without opening tools or
   writing preferences. An unavailable logo falls back to the text brand.
3. Choose and order the built-in widgets: application launcher, shared shortcuts
   and personal pins, organization links, account tools, Chat/notifications, and
   current deployment environment. Set positions from 1 to 6; catalog order
   breaks ties. On phones, shortcuts and organization links wrap below the
   primary tools. Brand and host-owned sign-out remain available. These are a
   declarative widget catalog, not arbitrary JavaScript, CSS, HTML, or iframes.
4. Select up to twelve **Shared application shortcuts**. Users see only deployed
   instances they can access, checked live against service permissions,
   classification tags, environment, and enabled/running state. Shared shortcuts
   and personal pins are deduplicated. Shared links never create permission grants.
5. Add up to eight organization links, set their order, choose whether they open
   a new tab, and optionally require organization permission tags. All selected
   tags apply live to the user and, in an integrated app, its backend identity.
   MFA freshness and purpose requirements still apply; tagged URLs and labels
   are omitted entirely when access is denied. The destination must enforce its
   own authentication and authorization. New tabs use `noopener noreferrer`.
6. Select **Show the shared header by default**, then **Save shared header**. New and existing
   organizations default to enabled. Disabling it restores Core's basic account
   header and changes the default consumed by integrated apps. Changes appear on
   the next visible-page refresh (normally within five seconds); reload an app
   that had the header disabled. **Reset header appearance** restores colors,
   logo, spacing, widgets, shared shortcuts, and organization links. It preserves
   the platform name, enable/override settings, personal pins, roles, and grants.
7. For an installed application, open **Set service access → Shared organization
   header**. Choose **Organization default**, **Show shared header**, or **Use
   application header**. Overrides apply to that application's deployed instances.
8. Assign users the application's actual service permissions and any deployment
   environment or classification tags. A bookmark never grants app access.
9. For Chat in an external app, grant the app `chat.read` and, if appropriate,
   `chat.send` in its declared marketplace capabilities. Add its installation as
   an approved participant in the relevant conversations. Users still require
   their own Chat permissions and conversation membership. A reader participant
   or a user without `chat-send` gets a read-only drawer.

Configuration does not inject code into arbitrary Kubernetes workloads. Existing
apps add the component and backend adapter below once. Apps generated by the
platform's app factory include both automatically; regenerate/review/redeploy an
older generated app to pick up the integration. Core's native pages already use
the header. All runtime targets use the same integration contract.

## Use it as a member

1. Sign in and select your organization. The header follows the selected
   organization across Core's pages; **Organizations** switches organizations.
2. Select **Apps**. Only active, running, permission-authorized deployed application
   instances appear. Each instance shows its environment and reported status.
3. Select the star to pin or unpin an app. Pins persist per user and organization,
   across sessions and integrated apps, up to twelve pins. Their order is the
   order pinned. Revoked, stopped, disabled, or inaccessible apps disappear on
   refresh even if their bookmark is retained. Apps must enforce their own live
   authorization when opened.
4. Select **Chat** in the header. Its badge counts notifications using each
   conversation's all/mentions/muted preference; unread messages remain visible
   when muted. Open a conversation to read or send. Reading at the bottom of a
   visible drawer advances your personal read marker; background polling does not.
5. Select **Open full Chat workspace** for the broader conversation tools.

## Integrate a deployed application

Use the app's existing OIDC authorization-code flow with PKCE, exact redirect URI,
and `openid authorization` scopes. Keep the user access token and workload token
on the app's backend. Its browser session must be HttpOnly, secure outside local
development, and protected against CSRF. `CoreClient.from_environment()` uses the
mounted workload credential and platform/environment metadata from the deployment
bundle. The integration discovery document now includes `header_url` and
`header: {enabled, mode, component_url}`. Do not treat a cached enabled flag as a
permission decision.

Serve `platform_services/assets/header.js` from your application (the generated
app does this), or load Core's public `/user-tools/header.js` script from your
configured issuer. Add this element after establishing the application's session:

```html
<script src="/header.js" defer></script>
<core-header endpoint="/core-header/"
             organization-id="YOUR_CONFIGURED_ORGANIZATION_UUID"
             csrf-token="YOUR_SESSION_CSRF_TOKEN"></core-header>
```

The organization ID comes from trusted deployment configuration. The CSRF value
is an anti-forgery token, not an OAuth or workload credential. A host can supply
an account/logout control in the `account` slot; the host handles its own logout
and invalidates its session. A purpose-protected application must supply its
approved current purpose to `CoreClient.purpose_code` on every adapter call. Never
reuse one user's purpose, preferences, or token in another user's request.
The component's optional `purpose-code` attribute sends the selected purpose in
`X-Core-Purpose`; the backend must still validate it through Core's policy.

Mount a same-origin backend route at `/core-header/`. Authenticate the session,
validate the request Origin and session CSRF token on POST, enforce bounded JSON
bodies, then pass only the session's server-held OAuth token to the adapter:

```python
from core_client import CoreClient, CoreServiceError
from header_client import HeaderAdapter

# Inside an authenticated, CSRF-protected application request:
core = CoreClient.from_environment()
core.purpose_code = current_approved_purpose
result = HeaderAdapter(core).handle(
    request_method,
    suffix_after_core_header_prefix,
    user_access_token=server_session_user_access_token,
    payload=validated_json_body,    # None for GET
    query=single_value_query_args,
)
```

Return JSON with `Cache-Control: no-store`. Map `CoreServiceError.status` to
400/401/403/404/409/503; return 503 on upstream errors without leaking tokens or
exception details. The adapter accepts a fixed route/field allowlist, never an
arbitrary URL or supplied user identity. The component sends `X-CSRFToken` on
same-origin POSTs. No CORS permissions, browser Bearer tokens, cross-origin
iframes, or third-party cookies are required. Tokens are refreshed using the
host's OIDC session lifecycle; an expired/revoked token fails closed.

The generated WSGI app supplies a working example in
`platform_services/app_factory_templates/server.py`: `/core-header/` requires its
native session and independently verifies its CSRF token and configured Origin.

The header state also contains `appearance` (validated colors, logo URL, spacing,
widget order, and organization-label preference), authorized `shortcuts`, filtered
`links`, and the current deployment `environment`. The version-1 contract remains
compatible with existing adapters. Use the current header component asset in
existing applications to render the added settings; new generated apps include it.
Organization branding applies even when an app explicitly overrides the header to
enabled. The state is per user and must never be cached between users or tenants.

Logos are browser-loaded images; Core never fetches an administrator's URL.
They need a public HTTPS image endpoint without credentials, signed query strings,
or fragments. A restrictive application CSP must permit the approved image origin
in `img-src` (or `https:` for configurable public image hosts). The generated app
uses `img-src 'self' https:`; local development additionally permits loopback HTTP
images. Scripts and styles remain restricted to the application origin. Browser
image loading uses `referrerpolicy="no-referrer"`, and failed/CSP-blocked images
fall back to text. Custom links use HTTPS; DEBUG-only local HTTP links and images
allow testing without provisioning external hosting. No image upload/storage or
third-party widget provider is required.

## Backend contract and security

All external calls use `Authorization: Bearer <application workload token>` and
`X-Core-User-Token: <the signed-in user's access token>`. This is a trusted-backend
contract. Bare workloads and AI agents cannot access personal pins or a human's
inbox. Tokens must belong to the same organization, calling service, and exact
credential deployment/environment. Both user and calling app policies are checked
live; there are no implicit grants from a header, pin, marketplace installation,
or agent-generated message.

| Route under `/api/platform/v1/header/` | Method | Purpose |
| --- | --- | --- |
| root | GET | Resolved header setting, brand, user tools, eligible apps, pins, authorized Chat activity |
| `pins/` | POST | `{deployment_id, pinned}` for the authenticated user |
| `chat/<conversation UUID>/messages/` | GET | Recent authorized messages, or `?after=<cursor>`, and live `can_send` |
| `chat/<conversation UUID>/send/` | POST | `{request_id, text, reply_to?}`; server-attributed and idempotent |
| `chat/<conversation UUID>/preferences/` | POST | Personal `{cursor?, notifications?}`; monotonic read marker |

Responses include `organization_id`; Chat responses also bind `conversation_id`.
The SDK pins those boundaries. Native Core uses session/CSRF endpoints under
`/organizations/<slug>/tools/` with the same behavior. Private responses are never
cached. User membership, role, tags, MFA freshness, purpose, application grants,
participant status, and federation authority approvals remain live checks.
Unread counts avoid per-message audit writes; policy decisions and preference
changes emit metadata-only audits. Chat messages sent through an application
record its installation as well as the human sender.

The component uses isolated styles and text nodes for user content, validates
link schemes, preserves drafts while polling, and rejects late responses after
revocation or changing conversations. Cross-instance conversations remain at
their approved authority and appear when that user and app are authorized; the
header adds no federation trust. No message history is copied into the header.

Polling runs every five seconds while the page is visible. Activity is bounded
to 100 joined conversations and 200 unread messages per conversation, with a
`200+` badge; the drawer loads 100 messages at a time. Header notifications are
in-app notifications. The full Chat workspace offers opt-in browser desktop
notifications while open; this feature does not add offline push or SMS/email
delivery. No paid notification provider or application deployment is activated.
